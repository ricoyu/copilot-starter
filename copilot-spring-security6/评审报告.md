# 代码评审报告：copilot-spring-security6

> 评审时间：2026-09-18　范围：src/main/java 全部源码 + pom.xml + META-INF 自动装配
> 分级：P0＝线上可触发；P1＝可靠性与正确性；P2＝性能/配置陷阱/技术债
> 标注：【复核确认】＝评审人读源码原文核对；【实测】＝探针/上游源码核对过；【分析】＝代码路径推导，需特定环境复现

## 概述
认证授权库（登录过滤器链、验证码、反重复提交、XSS 包装、安全上下文工具）。先说结论性的好消息：运行期认证走 `AuthUtils.checkToken`（Redis），`Jwts` 工具类在本模块零调用；jjwt 0.10.8 的 `parseClaimsJws` + Key 类型绑定会拒绝 `alg:none` 与密钥类型不匹配，**不存在 JWT 算法混淆/签名绕过**。过滤器实际顺序 SecurityExceptionFilter → PreAuthenticationFilter → VerifyCodeFilter → 用户名密码过滤器，顺序本身正确。问题集中在验证码与令牌生命周期。

## P0
### 1. 硬编码万能验证码 "ssy666"
`.../security6/filter/VerifyCodeFilter.java:56-61`
- 代码用 `"ssy666".equalsIgnoreCase(verifyCode)` 直接放行登录。任何知道这个字面量的人（这份脚手架的每个使用者、README、离职同事）都可对任意 codeId 提交 ssy666 跳过图片验证码；本模块登录又没有任何失败限速（见 P2#8），等于对 /login 开放无限次撞库。【复核确认：源码原文在 line 57】
- 修复：删除。确需调试后门则限定 dev profile + 配置项默认关闭 + 打审计告警日志。

## P1
### 2. 验证码通过后不删除，可无限复用且不绑定任何人
`VerifyCodeFilter.java:71-83`
- 注释写了「验证码用过之后删除」，但 line 82 之前没有任何 `del`；校验 key 仅由攻击者提交的 `codeId` 决定，不绑定用户/会话/IP；错误尝试不计数。
- 影响：一个通过的 codeId 在 5 分钟 TTL 内可并发用于任意账号登录，相当于一张固定通行证。【复核确认：注释后代码缺失属实】
- 修复：用 GETDEL/Lua 原子取出即删；失败 N 次删除该 codeId；生成时把 codeId 与 IP/会话指纹绑定，校验时比对。

### 3. 验证码文本用毫秒种子的 java.util.Random，可预测
`.../security6/utils/VerifyCodeUtils.java:60-63`
- `Random rand = new Random(System.currentTimeMillis())` 生成码文本；`rand.nextInt(codesLen - 1)` 还有 off-by-one，字符表最后一个字符（'Z'）永远不会出现，样本空间进一步缩水。文件底部 genImage 里用的是 SecureRandom，但那只影响干扰线/噪点，码文本不受保护。
- 影响：攻击者截获一张码图 + 知道大致生成时刻，可反推种子算出同窗口/后续验证码。【复核确认：60-63 行原文；「干扰线用 SecureRandom、正文不用」的对比属实】
- 修复：码文本改 SecureRandom；`nextInt(codesLen)` 用全字符空间。

### 4. TokenBasedAntiDupSubmitIntercepter 把完整 access token 拼进 Redis key
`.../security6/intercepter/TokenBasedAntiDupSubmitIntercepter.java:60-66`
- key 模板 `anti:dup:submit:{method}:{token}` 含明文令牌；任何能执行 KEYS/SCAN/MONITOR 的人（运维、同机低权进程、慢日志/AOF 文件）可直接读出在线会话令牌完成会话劫持。另外 line 60-63 token 为空时注释说「跳过检查」，实际 `return false` 拦截请求且不给任何响应体（空 200），行为与注释相反。【复核确认】
- 修复：key 用 `SHA-256(token)`；token 缺失按产品语义明确返回 401 JSON。

### 5. AuthenticationToken 反序列化完全信任输入里的 authenticated/authorities
`.../security6/deserializer/UsernamePasswordAuthenticationTokenDeserializer.java:55,82-88`
- `authenticated` 布尔与 `authorities` 列表直接从 JSON 读取，`if (authenticated)` 就构造「已认证」token。能控制被反序列化 JSON 的一方（共享 Redis 环境里可写缓存的低权进程、把该 mapper 用于外部输入的调用方）可伪造 `authenticated:true + authorities:["*"]` 的任意身份，与 spring-session CVE-2022-31692 同类。【实测(子代理)：反序列化器全文；利用前提见 uncertain】
- 修复：忽略输入中的 authenticated，一律构造未认证 token 交给 AuthenticationManager 重新认证；该 mapper 限定只用于受信任存储。

### 6. Jackson mixin 使用无白名单的 @JsonTypeInfo(Id.CLASS)
`.../security6/mixin/UsernamePasswordAuthenticationTokenMixin.java:27`（UserMixin.java:26、GrantedAuthorityMixIn.java:17 同型；由 ObjectMapperBeanPostProcessor.java:50-58 注入全局 ObjectMapper）
- `@JsonTypeInfo(use=Id.CLASS, property="@class")` 没有包/子类型白名单，且 mixin 被加到容器全局 ObjectMapper 上。凡出现这些类型的多态位置，`@class` 值会走 `Class.forName` 实例化——经典 Jackson 反序列化利用面（JdbcRowSetImpl/TemplatesImpl）。当前主要消费点是 copilot-cache 存进 Redis 的 security 对象：Redis 一旦可被写入即远程代码执行路径。本仓库未启用 default typing，风险取决于上述前提。【实测(子代理)；【分析】无现成利用链，按最坏存储污染场景评估】
- 修复：换带白名单的 TypeIdResolver（仅允许 `org.springframework.security..`/`com.awesomecopilot..` 已知类型），或去掉 @JsonTypeInfo 改在自定义 Deserializer 内按字段显式重建。

### 7. 登录成功日志打印明文 token 与全量权限表
`.../security6/handler/LoginSuccessHandler.java:53-61,84-85`
- `log.info("用户: {} 登录成功, Token: {}", username, accessToken)` 把会话令牌写进 INFO 日志，line 61 再打完整权限 JSON。日志采集/ELK/值班任何能看到日志的人可接管任意在线会话。同时 TTL 硬编码 `long expires = 30L`，`LoginDurationService` 接口未接线。令牌熵本身可用（`uniqueKey` 底层在 commons-lang3 3.14 下为 SecureRandom）。【复核确认：56/61 行原文】
- 修复：日志只打前 6 位+掩码；权限列表降 debug 并脱敏；TTL 读配置/LoginDurationService。

### 8. principal 强转具体类 User，自定义 UserDetails 直接崩溃
`LoginSuccessHandler.java:57`
- `(User) SecurityContextHolder.getContext().getAuthentication().getPrincipal()`——业务方返回自定义 UserDetails 实现（最常见写法）时登录成功瞬间 ClassCastException → 500，「密码对了却登录失败」。【实测(子代理)】
- 修复：按 `UserDetails` 接口编程（getUsername/getAuthorities）。

## P2
### 9. XSSRequestWrapper 清洗范围不对称，且在 security6 内已是死代码
`.../security6/http/XSSRequestWrapper.java:74-90,92-131`
- ①`getInputStream()/getReader()` 原样返回——JSON body 不清洗；`getParameterMap()` 未重写——从 map 读即绕过；`getHeaders` 按逗号拆散多值头再清洗，可能破坏 Cookie/Accept 语义。②`stripXSS` 先 `Encode.forHtml` 再 `Jsoup.clean`，双重转义会把含 `&`/`<` 的正常值改写坏。③commit 8c3875d 删除了唯一注册点 XSSFilter，本模块已无代码实例化该 wrapper——防护整体处于失效/死代码状态；`CopilotXSSProperties(prefix=copilot.xss)` 与 web-starter 实际生效的 `copilot.filter.xss-enabled` 前缀还不一致。【实测(子代理)读全文件+git log】
- 修复：要么删掉并在文档声明 XSS 在输出侧转义，要么补齐 body/map 清洗、去掉双重转义、统一配置前缀，并恢复注册点。

### 10. UserContextHolder.clear() 全仓零调用，ThreadLocal 清理靠外部可选件
`.../security6/utils/UserContextHolder.java:177-183`
- `clear()` 没有任何调用点；上下文（TransmittableThreadLocal 上的 USER_ID/LOGIN_INFO/ACCESS_TOKEN）清理依赖可选引入的 web-starter `ThreadLocalCleanupListener`，它只覆盖 Tomcat 请求线程。业务线程池（含 LoginSuccessHandler 内部 POOL）复用时上一用户上下文残留并被 TTL 带进异步任务；LoginSuccessHandler 登录时从 ThreadContext 捞 LOGIN_INFO 塞进新会话，存在把前一用户 loginInfo 串进当前用户记录的路径。【实测(子代理) grep 零调用】
- 修复：security6 自带 OncePerRequestFilter 在 finally 清理（模块自治）；登录路径显式传参。

### 11. PreAuthenticationFilter 写完响应又继续放行
`.../security6/filter/PreAuthenticationFilter.java:70-83,98-106`
- token 缺失分支 `writeJson` 提交响应后 `return null` 仍走链，后续 AuthorizationFilter 可能二次 writeJson（TOKEN_EXPIRED），最终客户端看到哪个错误码取决于提交顺序。【分析，取决于 RestUtils 对已提交响应的处理】
- 修复：写完直接 return；或只抛 InsufficientAuthenticationException 交给 EntryPoint 统一出参。

### 12. VerifyCodeFilter 与登录过滤器的路径匹配是两套解析
`VerifyCodeFilter.java:46` 对照 `CopilotWebSecurityAutoConfig.java:225`
- 前者用 servletPath+pathInfo（受 `;jsessionid`、容器规范化影响），后者用 AntPathRequestMatcher 对 requestURI + Boot3 默认 PathPatternParser。容器 normalize 配置差异下可能出现「验证码过滤器认为非登录路径、登录过滤器照常登录」的错位绕过。【分析：结构性隐患，需具体容器验证】
- 修复：两处复用同一个 RequestMatcher。

### 13. 登录失败错误码区分账号状态，可枚举用户
`.../security6/handler/LoginFailureHandler.java:32-55`
- ACCOUNT_LOCKED/DISABLED/EXPIRED/PASSWORD_EXPIRED 与密码错误各有独立错误码：未认证者可枚举「哪些账号存在且被锁」。且 `SpringSecurityExceptions.errorType` 精确类匹配，子类异常落到 INTERNAL_SERVER_ERROR。限速接口 RetryCountService 等在模块内零实现零调用，登录失败限速实际为零。【实测(子代理)】
- 修复：对外统一「用户名或密码错误」，细节进服务端日志；接线限速。

### 14. RestAccessDeniedHandler 是死 Bean，越权响应不守 REST 契约
`.../security6/handler/RestAccessDeniedHandler.java:29` 对照 starter 的 AutoConfig line 99
- 自动配置只挂了 authenticationEntryPoint，从未 `exceptionHandling().accessDeniedHandler(...)`；越权时走 Spring 默认 error page（HTML/whitelabel），与全 REST JSON 契约不符。方向仍是拒绝访问，属信息呈现缺陷。9d54377 重构引入。【实测(子代理)读 git log】
- 修复：AutoConfig 里把该 handler 挂上。

### 15. Jwts 与 File 版验证码输出的杂项
`.../security6/utils/Jwts.java:46-61`、`VerifyCodeUtils.java:117-123,224`
- Jwts 全模块零调用（死代码），且 `parseClaimsJws` 失败路径 `log.error("", e)` 全栈输出可被垃圾 token 刷日志，带 errorConsumer 时返回 null 让调用方 NPE。VerifyCodeUtils 的 File 版输出无 try-with-resources（ImageIO.write 抛异常即句柄泄漏+留下 0 字节文件），genImage 的 `g2.dispose()` 不在 finally。【实测(子代理)】
- 修复：Jwts 删除或改返回 Optional + 迁移 jjwt 0.12 API；File 版 try-with-resources，dispose 进 finally。
