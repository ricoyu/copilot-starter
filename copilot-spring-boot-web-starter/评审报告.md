# 代码评审报告：copilot-spring-boot-web-starter

> 评审时间：2026-09-18　范围：src/main/java 全部源码 + pom.xml + META-INF 自动装配 + resources
> 分级：P0＝线上可触发；P1＝可靠性与正确性；P2＝性能/配置陷阱/技术债
> 标注：【复核确认】＝评审人读源码原文核对；【实测】＝探针/上游源码核对过；【分析】＝代码路径推导，需特定环境复现

## 概述
Web 自动装配壳 + 限流/幂等/websocket 实现。最严重的问题是限流单位错配：注解按毫秒声明，Redis 脚本按秒生效，实际限流比声明宽 1000 倍。另有 5 个与库模块重复的孪生类（背景见 copilot-spring-boot-web 报告）。

## P0
### 1. 限流窗口单位错配：毫秒被当秒用，限流形同放宽 1000 倍
`.../intercepter/RateLimitIntercepter.java:71-76`
- 现象：`@RateLimit.window()` 注释和默认值都是毫秒（`RateLimit.java:49` `int window() default 1000;`，文档写「单位是毫秒」）；拦截器把 `timeWindow` 原样传给 `JedisUtils.AFFLUENT.rateLimit(key, timeWindow, limit)`，而该方法（awesome-copilot JedisUtils.java:2578-2593）把它作为 `ARGV[1]` 进 `rateLimit.lua` 的 `redis.call('expire', KEYS[1], ARGV[1])` —— Lua `EXPIRE` 的单位是秒。
- 影响：默认配置 `@RateLimit(limit=100, window=1000)` 实际执行的是「1000 秒内 100 次」。限流比声明宽约 1000 倍，对攻击者几乎不设防，且日志与响应看不出任何异常。【实测：注解原文、JedisUtils 源码、rateLimit.lua 三者均在本机读原文核对】
- 修复：调用处换算 `(int) Math.ceil(window / 1000.0)`，或把注解契约改为秒（连同 javadoc）；补一个观察 Redis TTL 的回归测试。

## P1
### 2. 拦截器取 @RequestMapping 的两条 NPE 路径
`RateLimitIntercepter.java:54-61`
- ①类级 `@RequestMapping` 在 Spring MVC 是可选的，控制器没写时 `controllerMapping` 为 null，line 55 NPE；②`handlerMethod.getBean().getClass()` 拿的是代理类，CGLIB 代理的控制器（如加了 `@Transactional`）上 `@RequestMapping` 没有 `@Inherited`，`getAnnotation` 返回 null——真实类有注解照样 NPE。
- 影响：命中 `@RateLimit` 的接口每个请求 500。【实测(子代理)，规则确定】
- 修复：改 `AnnotatedElementUtils.findMergedAnnotation(handlerMethod.getBeanType(), RequestMapping.class)` + null 保护；方法级同理用 `handlerMethod.getMethodAnnotations()`。

### 3. Redis 故障时限流器把整个 API 拖下水（意外 fail-closed）
`RateLimitIntercepter.java:76`
- `JedisUtils.rateLimit` 把脚本 SHA 缓存在 static map、直接 `evalsha`，没有 NOSCRIPT 重加载，也不处理连接异常（awesome-copilot JedisUtils.java:2578-2592）。Redis 宕机/重启/脚本被淘汰时 `preHandle` 抛出，所有 `@RateLimit` 接口返回 500——限流组件把 Redis 的一次故障放大成 API 整体不可用。【实测(子代理)读上游源码；建议连真实 Redis 验证】
- 修复：拦截器捕获异常后按明确策略降级：fail-open 放行并计数告警，或本地内存限流兜底；NOSCRIPT 时重新 scriptLoad 再试。

### 4. 限流计数 key 无用户维度 + 算法名不副实 + 429 未设状态码
`RateLimitIntercepter.java:69,75,95-99`
- ①key 只有 `rate_limit:controllerPath:methodPath`，一个滥用者烧光共享配额，全站用户被锁；②枚举只有 `SLIDING_WINDOW`，但 Lua 是 `INCR+EXPIRE` 固定窗口——窗口接缝处可打出 2 倍突发，算法标签与实现不符（JedisUtils 里其实已有 ZSET 滑动窗口 `slidingWindows` 可用）；③限流命中路径 `response.setStatus` 从未调用，HTTP 层返回 200 包着业务错误码，监控与客户端重试逻辑看不见限流；响应头 `Access-Control-Allow-Headers ` 尾部多个空格，浏览器直接忽略。【复核确认：源码逐行核对】
- 修复：key 加用户/IP 维度；改真实滑动窗口或如实改名；`setStatus(429)`；删头名尾部空格。

### 5. 5 个孪生类随两个 jar 重复发布（同全限定名）
`copilot-spring-boot-web-starter/pom.xml（依赖 copilot-spring-boot-web）+ 5 对同名类`
- `RateLimit/RateLimitHandler/RateLimitIntercepter/WebSocketFilter/IdempotentTokenController` 五个类在两个 jar 里以相同全限定名各一份（前四个字节级一致，controller 仅注释差异，diff 实测）。当前「活的」是 starter 这份（imports 只注册 starter 的 autoconfig；web 库无 imports）。同名双份意味着加载哪份取决于 classpath 顺序，未来单侧修改即静默漂移。【实测(子代理 diff)，狗蛋复核 imports 注册面】
- 修复：从 starter 删除这 5 个副本类，直接引用库 jar 中的类；或反向收敛。

## P2
### 6. 自动配置缺条件注解，用户覆盖会撞名失败
`.../autoconfig/CopilotMvcConfiguration.java:86-91,112-131,153-156`
- `conversionService()`、`characterEncodingFilter()`、`apiSignFilter()`、`tenantIdFilterRegistration()` 均无 `@ConditionalOnMissingBean`（同文件里 `globalBindingAdvice`/`restExceptionAdvice` 却有，标准不一）。用户定义同名/同型 Bean 时，Boot 3 默认禁止 bean 定义覆盖，直接启动失败 `BeanDefinitionOverrideException`；`tenantIdFilterRegistration` 甚至没有任何配置开关可关。【实测(子代理)】
- 修复：逐个补 `@ConditionalOnMissingBean`，过滤器注册加 `@ConditionalOnProperty`。

### 7. imports 里的类用 @Configuration 而非 @AutoConfiguration
`.../autoconfig/CopilotWebAutoConfig.java:20-25` 等
- `CopilotMvcConfiguration`/`CopilotWebAutoConfig`/`CopilotLocaleConfiguration` 以普通 `@Configuration` 列进 AutoConfiguration.imports：拿不到自动配置之间的排序语义（`@AutoConfigureBefore/After`），也没挂 `@ConditionalOnWebApplication(SERVLET)`——`RateLimitIntercepter` 与 `PageResultAspect` 在任何环境下都被注册。`CopilotLocaleConfiguration.java:64-72` 的 `localeResolver` 无 ConditionalOnMissingBean，与用户自定义同名 Bean 冲突。【实测(子代理)】
- 修复：改 `@AutoConfiguration` + `@ConditionalOnWebApplication(type=SERVLET)`；补覆盖条件。

### 8. 租户必填开关有两个真相源
`CopilotMvcConfiguration.java:65-66,127`
- mandatory 经 `@Value("${copilot.filter.tenant.mandatory:false}")` 在启动时快照进 filter 构造器，而结构化配置 `CopilotFilterProperties.Tenant.mandatory`（CopilotFilterProperties.java:73）存在却不被读取（filter 只惰性读它的 excludeUrls）。用户改哪边、何时生效不一致。【实测(子代理)】
- 修复：把 `CopilotFilterProperties` 注入 `TenantIdFilter`，每请求读 `isMandatory()`，删 `@Value`。
