## P1
### 1. 幂等令牌存进全局单 SET，无 TTL 无清理 ✅已修复（2026-09-20）
`.../rocketmq5x/aspect/RocketMQ5xIdempotentAspect.java:78-93`
- 所有消息的 uniqueValue `SET.sadd(KEY)` 进同一个 Redis key（`rocketmq:idempotent`，常量见 RocketMQ5xConstants.java:13），无任何过期设置，只有业务异常分支 srem。成功消费的成员永久驻留：这个 SET 随消息量单调增长（单 key 大 SET 还拖累持久化与集群 slot 均衡）；「幂等窗口」完全不可配置。【复核确认：sadd/srem/常量读原文】
- 修复：改每消息独立 key `SET idem:{uniqueValue} 1 NX EX ttl`（ttl 取消息最大重试跨度，如 24h/72h），NX 失败才算重复；失败路径 DEL 释放保留。
- **修复记录**：令牌存储改为每令牌独立 key `rocketmq:idempotent:{uniqueValue}`，用 `JedisUtils.setnx(key, value, expires, timeUnit)`（上游 lua 脚本实现的原生"NX+过期"原子操作，读 JedisUtils.java:422 与类注释确认存在）；NX 失败即重复消费；消费失败 `JedisUtils.del(redisKey)` 释放令牌。幂等窗口可配置：`copilot.rocket5x.idempotent.ttl-seconds`（默认 14400 秒=4 小时，覆盖 RocketMQ 默认 16 次重试的跨度），经 `CopilotRocketMQ5xAutoConfig.rocketMQ5xIdempotentAspect(properties)` 注入构造器。旧常量 `RocketMQ5xConstants.KEY` 标 `@Deprecated` 保留（全仓 grep 除本切面外无引用）。回归测试：`bizKeysNoLongerUsedAsUniqueValue` 断言 TTL 以构造参数进入 `acquireToken(uniqueValue, ttl)`、`redisKeyIsPerTokenWithPrefix` 断言 key 形态。⚠️ 升级注意：旧全局 SET 里已驻留的历史令牌不会被新实现读到也不会被清理——上线后需手工 `DEL rocketmq:idempotent`（旧 SET）一次，否则它永远占着内存；切换瞬间旧 SET 中"已消费"的消息若重投，新 key 空间判不出重复，会有一个 TTL 周期的重复消费暴露窗口——建议低峰发布。

### 2. 以 msg.getKeys() 作为判重降级取值会误丢正常消息 ✅已修复（2026-09-20）
`RocketMQ5xIdempotentAspect.java:79,106-109`
- uniqueValue 优先级里含 `msg.getKeys()`。RocketMQ 的 keys 是业务键：生产者常以订单号等设置，且有意给多条消息共用同一 key、一个 key 字段本身可空格分隔多值。同一订单先后两条不同消息，第二条命中 SET 被当「重复消费」直接确认丢弃、无告警——真丢数据。keys 缺失/多值分支未处理。body 为 null 时 line 79 `new String(msgExt.getBody(), UTF_8)` 抛 NPE 被包成 RuntimeException，消息进无限重试。line 83/92 还把全量消息体 info 进日志（PII/金额泄露+日志量大）。【实测(子代理)；【分析】丢消息触发条件依赖业务 keys 用法】
- 修复：降级取值改 `msg.getMsgId()`（RocketMQ 原生唯一）；业务 keys 判重须显式声明；日志只打 uniqueValue 与 body 长度；body 判空。
- **修复记录**：唯一标识取值顺序改为——注解 `key` 指定的用户属性 → 内置 `UNIQ_KEY` 用户属性（RocketMQ 客户端发送时自动写入，`MessageClientIDSetter` 设置的就是它；旧版注解 javadoc 承诺的一直是这个，代码却从未读取，本次补上）→ `msg.getMsgId()`。`msg.getKeys()` 彻底移出自动链路：要按业务号判重必须显式 `@RocketMQ5xIdempotent(key="...")` 指向发送端塞的用户属性。日志不再输出消息体内容，只带 uniqueValue。body 判空不再需要——新实现根本不读 body。回归测试：`bizKeysNoLongerUsedAsUniqueValue`（设了业务 keys 的普通消息，令牌取 msgId 不取 keys）、`nullBodyFallsBackToMsgIdWithoutNpe`（body=null 正常消费）、`logsCarryUniqueValueNotBodyContent`（断言日志不含消息体内的 amount/idCard 字样）。

## P2
### 3. Redis 故障与重复返回值的边界 ✅已修复（2026-09-20）
`RocketMQ5xIdempotentAspect.java:38-95`
- ①Redis 不可用时 sadd 的 JedisConnectionException 原样抛出→全 topic 消息进重试风暴，无 fail-open 开关（可用性完全绑定 Redis）；②重复消费分支 `return null`：标注方法返回 `ConsumeConcurrentlyStatus` 等枚举时，null 交给 rocketmq-spring 2.3.0 的判空逻辑可能 NPE 或误判成功——注解实际只该用于 void 消费方法但未校验；③业务异常 `throw new RuntimeException(e)` 双重包裹丢失原异常类型。【实测(子代理)；容器判空行为需真实环境验证】
- 修复：Redis 异常提供 fail-open/fail-closed 配置；非 void 返回类型启动期拒绝注册；重抛保留原异常。
- **修复记录**：①Redis 异常策略开关 `copilot.rocket5x.idempotent.fail-open-on-redis-error`，默认 false=fail-closed（抛回使容器重试，宁可延迟消费不做无保护消费）；配 true 后 Redis 故障期间放行消费并记 error（幂等保护暂停，可用性优先）。测试两向各一例：`redisDownFailClosedRethrowsForRetry`、`redisDownFailOpenSkipsIdempotencyAndProceeds`。②返回类型校验（**本条初版设计有误，见下方第二轮修订**）。③业务异常改为原样重抛（切面方法声明 `throws Throwable`，不再 `new RuntimeException(e)` 包裹），调用方对原异常类型的判断保持有效（`businessExceptionReleasesTokenAndKeepsOriginalException` 断言 `isSameAs(original)`）。
- **②的修订（2026-09-20，第二轮独立评审实测纠正）**：初版实现假设"消费方法可能返回 ConsumeConcurrentlyStatus/ConsumeOrderlyStatus，重复消息要按类型回 CONSUME_SUCCESS/SUCCESS"，并声称旧版"return null 交给 rocketmq-spring 判空可能误判"。评审拆 rocketmq-spring-boot 2.3.0 sources 证伪：`RocketMQListener.onMessage` 声明为 **void**，容器 `handleMessage` 调用后**丢弃返回值**，并发/顺序监听器只按"有没有抛异常"返回 RECONSUME_LATER/CONSUME_SUCCESS（`DefaultRocketMQListenerContainer` 源码 400-465 行，本方已复读确认）。因此：状态枚举返回值从未被容器读取，"误判成功"的前提不存在；返回状态枚举的方法根本不满足 `RocketMQListener` 接口，是误用形态；而真正读返回值的是应答式 `RocketMQReplyListener`（容器把返回值回写给请求方），初版白名单放它进来会替它构造错误应答。最终设计：**只允许返回 void**——void 方法重复时正常返回（不抛异常）即被容器确认跳过，语义天然正确；非 void（含状态枚举与应答式）首次调用即抛 IllegalStateException 点名方法，切面不猜它该回什么。删除 `duplicateAck`，新增回归 `statusReturningMethodIsRejectedAtFirstCall`、`otherReturningMethodRejectedAtFirstCall`。⚠️ 行为变化：上一版本文档曾承诺"支持状态返回方法"，实际该形态从不可用变为明确报错，readme 已同步收紧。

## 独立评审状态（2026-09-20）
本批改动的独立评审代理运行 34 分钟后因模型配额耗尽中断，未产出最终结论。派单时指定的 6 个核查点由评审人（狗蛋）自行完成，证据如下：
1. **setnx 重载解析**：调用形如 `setnx(String, String, long, TimeUnit)`，上游四个重载（JedisUtils.java:382/394/407/422）中唯一 4 参版本是 `(String, Object, long, TimeUnit)`——实参正确命中该方法。
2. **setnx.lua 原子性**：脚本原文 `local set = redis.call("setnx", KEYS[1], ARGV[1]); if set==1 then expire(...); return set`——NX 判定与过期设置在一次 Lua 执行内完成，并发双消费者同一消息时恰有一个拿到 `1`，另一个拿到 `0` 走重复消费分支（预期语义）。**遗留小缺陷如实记录**：若 setnx 成功后、expire 执行前进程崩溃（Lua 单命令间非跨语句持久），该 key 会不带 TTL 驻留——与旧版"永不过期"同型但范围缩到单个卡住的令牌，重启后不会误判（key 存在即判重复，恰为所需语义），仅内存回收退化；如需彻底消除可改 `set key val NX EX`（Redis 2.8+ 原生一条命令），当前 JedisUtils 未提供该形态，暂不引入。
3. **UNIQ_KEY 写入方**：rocketmq-common jar 内 `MessageClientIDSetter` 字节码确认客户端发送时 `createUniqID()` 并写入属性 `UNIQ_KEY`（javap 常量池命中 `String UNIQ_KEY`），消息属性随消息体存储、broker 重投不改变——判重首选它成立。msgId 作为最后一级取值的已知局限：push 消费 `MessageExt.getMsgId()` 返回 broker 存储位点 id，重投后可能变化，故只用于"不带 UNIQ_KEY 的消息"（如外部工具投递），同一消息的投递重试场景它不保证稳定——注解 javadoc 的"建议业务自行生成唯一标识塞消息属性"仍是强一致场景的正解。
4. **value 序列化**：`ByteUtils.toBytes` 对 String 直接 UTF-8 字节（源码 35-36 行），不走 Jackson，key/value 均无序列化歧义。
5. **返回类型白名单外的 throw**：`@Around` 抛出沿 rocketmq-spring 监听回调传给容器，效果等同业务异常——消息进重试、16 次后入死信队列并带明确异常栈；该场景本身是编码错误，消息不丢、错误可定位，可接受。（**勘误**：此条论证的异常去向仍然成立，但白名单本身的设计前提被第二轮评审推翻，见文末第二轮补记必须修4。）
6. **ttl 断言一致性**：测试 FakeAspect 用 3600 只是验证"构造参数按原值传给 acquireToken"的传递链；生产默认 14400 定义在 `CopilotRocketMQ5xProperties.Idempotent.ttlSeconds`，由自动配置注入，两值不同是有意区分。
