## 概述
RocketMQ 5.x 消费幂等 starter。异常路径处理正确（业务异常释放令牌后重抛→容器 RECONSUME_LATER，不吞消息），但幂等令牌存储、keys 判重口径与依赖版本各有一个要紧问题。

## P1
### 1. 幂等令牌存进全局单 SET，无 TTL 无清理
`.../rocketmq5x/aspect/RocketMQ5xIdempotentAspect.java:78-93`
- 所有消息的 uniqueValue `SET.sadd(KEY)` 进同一个 Redis key（`rocketmq:idempotent`，常量见 RocketMQ5xConstants.java:13），无任何过期设置，只有业务异常分支 srem。成功消费的成员永久驻留：这个 SET 随消息量单调增长（单 key 大 SET 还拖累持久化与集群 slot 均衡）；「幂等窗口」完全不可配置。【复核确认：sadd/srem/常量读原文】
- 修复：改每消息独立 key `SET idem:{uniqueValue} 1 NX EX ttl`（ttl 取消息最大重试跨度，如 24h/72h），NX 失败才算重复；失败路径 DEL 释放保留。

### 2. 以 msg.getKeys() 作为判重兜底会误丢正常消息
`RocketMQ5xIdempotentAspect.java:79,106-109`
- uniqueValue 优先级里含 `msg.getKeys()`。RocketMQ 的 keys 是业务键：生产者常以订单号等设置，且有意给多条消息共用同一 key、一个 key 字段本身可空格分隔多值。同一订单先后两条不同消息，第二条命中 SET 被当「重复消费」静默 ACK 丢弃——真丢数据。keys 缺失/多值分支未处理。body 为 null 时 line 79 `new String(msgExt.getBody(), UTF_8)` 抛 NPE 被包成 RuntimeException，消息进无限重试。line 83/92 还把全量消息体 info 进日志（PII/金额泄露+日志风暴）。【实测(子代理)；【分析】丢消息触发条件依赖业务 keys 用法】
- 修复：兜底优先级改 `msg.getMsgId()`（RocketMQ 原生唯一）；业务 keys 判重须显式声明；日志只打 uniqueValue 与 body 长度；body 判空。

## P2
### 3. Redis 故障与重复返回值的边界
`RocketMQ5xIdempotentAspect.java:38-95`
- ①Redis 不可用时 sadd 的 JedisConnectionException 原样抛出→全 topic 消息进重试风暴，无 fail-open 开关（可用性完全绑定 Redis）；②重复消费分支 `return null`：标注方法返回 `ConsumeConcurrentlyStatus` 等枚举时，null 交给 rocketmq-spring 2.3.0 的判空逻辑可能 NPE 或误判成功——注解实际只该用于 void 消费方法但未校验；③业务异常 `throw new RuntimeException(e)` 双重包裹丢失原异常类型。【实测(子代理)；容器判空行为需真实环境验证】
- 修复：Redis 异常提供 fail-open/fail-closed 配置；非 void 返回类型启动期拒绝注册；重抛保留原异常。

### 4. aspectjweaver 1.8.7 与 JDK21/Boot 3.2 不匹配
`copilot-spring-boot-rocketmq5x-starter/pom.xml`（aspectj 依赖，git show 0fcdfa2 引入）
- 写死 1.8.7（2015 年，最高识别 Java 8 字节码），工程线 Boot 3.2/Spring 6.1 要求 AspectJ 1.9.x：`@annotation` 切点在解析 records/泛型签名时有 `unsupported class file major version 65` 风险。与 starter 报告里 copilot-spring-boot-starter 的同名问题是同一批遗留。【实测(子代理)读 pom+git 历史】
- 修复：删版本号交给 Boot 管理。另注意 rocketmq-spring-boot-starter 2.3.0 是 Boot 2 时代产物（自动配置走旧 spring.factories 格式，Boot 3 不读取），本 starter 对它的依赖兼容性需专项验证。【分析】
