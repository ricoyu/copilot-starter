- 实际情况：`RedisListenerProcessor.java:5` 导入的是本项目 commons-lang 的 `com.awesomecopilot.common.lang.utils.ReflectionUtils`。其 `doWithMethods`（awesome-copilot commons-lang/.../ReflectionUtils.java:958-981）在递归父类前有判断：
  ```java
  // 获取父类, 但如果clazz是代理类的话就不找其父类了
  if (!clazz.getName().contains("$$") && clazz.getSuperclass() != null) {
      doWithMethods(clazz.getSuperclass(), mc, mf);
  ```
  代理类（类名含 `$$`）扫完自己声明的方法后就停止向上递归，所以每个 `@RedisListener` 方法在单个 bean 上只被扫描到一次，不存在「同一 bean 双份订阅」。撤销该条 P0。
- 仍然成立的两个事实（降级为 P2，见下）：① `methods` 去重字段（line 40）与 `toMethodName`（line 126）依然没有任何引用，是死代码；② 作者在 line 38 与 line 46-49 的注释记录过「实测」会拿到代理实例与原始实例两个 bean 因而重复注册——若该现象为真，重复来自 bean 集合层面（同一 bean 在父子容器/两个 Spring 上下文里各注册一份，导致 processor 自身被实例化两次），而不是方法扫描层面；去重逻辑没接线这一点在两处注释里都还成立。

### 2. psubscribe 监听方法抛异常会中断整条订阅连接 ✅已修复
`RedisListenerProcessor.java:113-117`
- 现象：回调里 `method.invoke` 抛异常后被 `catch`，记录 `log.error` 后 `throw new RuntimeException(msg, e)` 重新抛出。
- 原因：psubscribe 的回调在 Jedis 套接字读线程上同步执行（对照 awesome-copilot 的 JedisUtils.java:2923-2930，不像 subscribe 在第2899行有线程池跳转）。异常沿 onPMessage 传播出 JedisPubSub 的事件循环后，该连接上的整组 pattern 订阅（含同连接的其它监听器）一起失效，之后来的消息不再被处理，但进程仍然健康。
- 影响：一条异常消息就让某个 Redis 连接上所有 pattern 监听器停止接收消息，且没有任何明显信号。【代码分析，需连真实 Redis 抛一次异常验证后续消息是否断流】
- 修复：回调节流内 `catch Throwable`，只记录不重抛（或把 `method.invoke` 投递到独立线程池执行，与 subscribe 路径一致）；同时补 `ReflectionUtils.makeAccessible(method)`，否则 protected/private 监听方法首条消息就 `IllegalAccessException`。
- **修复记录（2026-09-18）**：`createMessageListener` 成为回调的唯一实现（subscribe/psubscribe 共用），`catch (Throwable)` 后只 `log.error`（日志带 channel 与消息内容，便于事后补发）不再抛出；注册时 `ReflectionUtils.makeAccessible(method)`；`messagePattern` 移到注册期预编译，非法正则启动即抛带方法名的 IllegalStateException（评审代理指出原修复版里正则编译仍在 try 块外，属同一故障模式，已按此闭环）。回归测试：`src/test/java/.../RedisListenerProcessorTest.java` 6 例（异常不传播、异常入日志含方法名与异常链、protected 方法可达、单参/双参传参分支、消息不匹配正则不消费、非法正则注册期抛出），surefire 结果 `Tests run: 6, Failures: 0`。⚠️ 行为变化：①监听方法抛异常从「中断该连接全部 pattern 订阅」变为「该条消息被跳过并记 error 日志，订阅继续」——消息丢失从连带伤害变为单条丢弃，靠日志定位补发；②`messagePattern` 写错的暴露时机从「首条消息到达时」提前到「应用启动时」，且启动直接失败（原先是订阅失效但应用显示正常）。

### 3. 双删切面在 JDK 动态代理下抛 NPE ✅已修复（2026-09-19）

### 4. 双删切面：延迟写死 + 无界队列 + 停机丢弃 ✅已修复（2026-09-19）
`CopilotCacheEvictAspect.java:33-38,64-74`
- 现象：延迟固定 1 秒（`scheduler.schedule(..., 1, SECONDS)`），单线程 `ScheduledExecutorService`，线程 `setDaemon(true)`，无 shutdown hook；每次调用 `parseSpelKeys` 都执行 `DynamicUtils.createObject`（第112行）。

- 说明：双删策略本身的时序（`@Before` 删 → 提交后延迟再删）和异常路径（删除失败仅记日志、不再向上抛出、业务异常不触发第二删）符合注释声明的设计，无逻辑错误。问题都在可配置性和资源侧。【实测(子代理)：版本号与调用链读自 pom/上游源码】
- 修复：延迟提为注解属性或 `copilot.cache.evict-delay-ms` 配置（默认 1000）；线程池注册 shutdown hook 先 `shutdown` 再 `awaitTermination`；rootObject 生成结果按「参数名集合」缓存，或改用 `StandardEvaluationContext.setVariable` 直接传参，不再每次造动态类。
