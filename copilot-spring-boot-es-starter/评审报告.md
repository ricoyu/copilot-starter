### 1. 模板文件名无扩展名 / 模板全空白时启动直接崩溃 ✅已修复（2026-09-20）
`.../es/autoconfig/CopilotESAutoConfiguration.java:110-127,137`
- ①`templateName` 只在 `dotIndex != -1` 时赋值，路径没有扩展名（如 `classpath:event_template`）时 line 115 `templateName.lastIndexOf("\\")` NPE；②所有模板内容读出来都是空白（line 83-85 continue）时 `templatePair` 为空，line 137 `templatePair.get(0)` IndexOutOfBoundsException。
- 影响：一个配置笔误导致应用启动失败，栈信息是 NPE/IOOBE，完全指向不到「模板文件名缺扩展名」这个根因。【实测(子代理)逐行；小赫复核分支逻辑】
- 修复：dotIndex==-1 或内容为空时 `log.warn` 带文件名后跳过（或抛带文件名的 IllegalStateException）；`templatePair.isEmpty()` 直接 return。
- **修复记录（2026-09-20）**：模板名解析提取为静态方法 `resolveTemplateName`：去 `classpath:` 前缀（含 `classpath:/` 形态）→ 按 `/` 与 `\` 取最后一段 → 去扩展名；文件名无扩展名时整段作模板名，不再出现「未赋值即调用 lastIndexOf」。`initTemplate` 重构：空白条目 warn 跳过；每个条目独立 try-catch，读取失败或内容为空记 error（带文件名与「检查文件路径与扩展名」提示）后跳过；有效条目为 0 时记 info 直接返回；并发分支每个模板的写入独立捕获、错误日志带模板名。回归测试：`src/test/java/.../CopilotESAutoConfigurationTest.java` 4 例（无扩展名不抛异常、四种路径形态解析出预期模板名、全无效条目返回空且不触碰 ES、混合条目只写有效模板——用覆写 `putIndexTemplate`/`pingCluster` 接缝的 RecordingConfig 隔离，夹具 `src/test/resources/templates/no_ext.tmpl`、`blank.json`），surefire `Tests run: 4, Failures: 0`；全仓 14 模块 test-compile 通过。实现细节说明：生命周期钩子从 `@PostConstruct` 改为 `InitializingBean.afterPropertiesSet()`（评审补记纠正：两者都在依赖注入完成后执行，探针实测 Spring 6.1.5 顺序为「属性填充→@PostConstruct→afterPropertiesSet」，旧代码不存在 environment 为 null 的问题，改钩子只是接口约定偏好）。⚠️ 行为变化：模板条目从「一个笔误=应用启动失败」变为「跳过该条目+error 日志，应用照常启动」。
- **独立评审补记（2026-09-20，评审代理复跑+12 组输入解析探针+生命周期探针）**：4 条必修与 7 条建议，处置如下——

### 2. 引入即初始化 transport client，无总开关 ✅已修复（2026-09-20，后经用户纠偏改为显式开启，见修订）
`CopilotESAutoConfiguration.java:30,54-77`
- 类是 `@Configuration` + `@PostConstruct`，无 `@ConditionalOnClass`/`@ConditionalOnProperty(enabled)`。引入 starter 就触发 `ElasticUtils` 类初始化：静态 `CLIENT = TransportClientFactory.create()` 读 classpath:elastic.properties 并建 9300 连接，ES 不可达则应用起不来。想「先引依赖、凭证后给」的用户直接卡死。
- 修复：补 `@ConditionalOnClass(ElasticUtils.class)` + `copilot.es.enabled` 总开关（matchIfMissing=true 保持兼容）。
- 关联提醒：底层 copilot-search 仍是 transport-client 7.9.3（ES 7.5+ 服务端已移除该协议），TASKS.md 中 8.x 迁移完成前这是一个已知升级阻塞点。
- **修复记录**：类上加了 `@ConditionalOnClass(ElasticUtils.class)` 和 `@ConditionalOnProperty(prefix="copilot.es", value="enabled", havingValue="true", matchIfMissing=true)`。默认行为与旧版一致（引入即初始化），新增 `copilot.es.enabled=false` 让整个配置类不装配、不加载 ElasticUtils。⚠️ 边界：enabled=true（默认）时连接照建、连不上照失败——开关提供的是「完全退出」的能力，没有改变默认路径。
- **修订（2026-09-20，用户指出 matchIfMissing 应为 false 后采纳）**：matchIfMissing=true 没有修到本条的病根——"不配置也算开启"意味着只要 jar 在 classpath 且 ES 不可达，应用照样起不来，开关只是个手动出口。改 `matchIfMissing=false`：显式配 `copilot.es.enabled=true` 才装配，缺省完全不建连接。改动前核查了引用面（全 D:\Learning 扫描：引用本 starter 的 pom 仅 copilot-starter 仓库自身两处，配置 copilot.es.* 的文件零处，无存量打断风险；私服/仓库外工程若在用需显式补 `enabled=true`）。新缺口的防呆：enabled 缺省 false 后"配了 templates/init 却忘开 enabled"会不生效且无提示，新增 `CopilotESUsageGuardAutoConfiguration`（不受 enabled 条件约束、总是装配，注册进 imports）——枚举 Environment 中发现任何 `copilot.es.*` 使用键（含 yml 列表的 `copilot.es.templates[0]` 带下标形态）而 enabled 不为 true 时，warn 点名该键并提示补 `copilot.es.enabled=true`。回归测试：`CopilotESUsageGuardAutoConfigurationTest` 4 例（有使用项未开→warn 点名、已开→无提示、无任何配置→无提示、缺省装配验证用 ApplicationContextRunner 实测 CopilotESAutoConfiguration bean 不存在）；连同原 8 例共 12/12 通过，全仓 test-compile 零错误。⚠️ 行为变化：升级本 starter 后 ES 功能默认关闭，现有应用必须显式配 `copilot.es.enabled=true` 才恢复旧行为。
- **对 guard 的独立评审补记（2026-09-20）**：评审确认「不会误提示」（warn 前置与 OnPropertyCondition 同源走 `Environment.getProperty`，-D/环境变量/非 Enumerable 源里的 enabled=true 都能解析到，装配了的绝不会收到提示），指出 1 处注释与实现不符 + 5 条建议，处置：
  - 必修（已修，纯文档面）：javadoc 声称覆盖"yml 列表与驼峰写法"，实为对原始键名字面匹配——环境变量形态（`COPILOT_ES_TEMPLATES` 下划线大写键）与自定义非 Enumerable 属性源里的使用项检测不到。缺口方向是"该提示时不提示"，不产生错误提示；javadoc 已如实声明这两类局限。
  - 建议2（已采纳，行为变更）：显式配 `copilot.es.enabled=false` 视为主动关闭，不再 warn——多环境工程在 prod 用 enabled=false 关掉、各 profile 保留全套 copilot.es.* 是常规做法，原实现每次启动给一个明确决定打一条 warn 属于固定噪声。新语义：仅"enabled 键完全缺失 + 存在使用项"才提示。回归测试 `explicitFalseEnabledMeansIntentionalOptOutAndStaysSilent`（先 RED 后转绿）。
  - 建议3（已补）：`guardRunsAtContextStartupWiring` 用 ApplicationContextRunner 带属性启动，证明 afterPropertiesSet 接线有效（原 3 例直调静态方法，删掉钩子调用测试仍全绿）。
  - 建议4（已补）：warn 消息断言同时含命中键名与补救键名（`warnNamesTheDetectedUsageKey`）；新增 imports 文件逐行 `Class.forName` 可解析测试（`autoConfigurationImportsResolveToRealClasses`，此前测试用类名直列绕过了注册文件，幽灵注册测不出来）。
  - 建议5（已写进 readme）：新增「升级注意事项」段，显式声明两条对外影响——enabled 缺省 false 的破坏性变更，以及**连带影响**（条件类不装配时其 `@EnableConfigurationProperties` 注册的 `CopilotESProperties` bean 也随之消失，直接注入该类的代码会因找不到 bean 在启动阶段直接报错, 而不是带着缺失的配置继续运行；本仓库 grep 零消费者，对外发布件需用户自查）。
  - 建议6（记录在案）：enabled 字段（仅 IDE 元数据）与条件注解读 Environment 构成两个写入点，当前默认值一致且 javadoc 标明真相归属；未加"字段默认值==matchIfMissing"的反射断言，留作低优先。
  - 建议7（已修）：`CopilotESAutoConfiguration` 由 `@Configuration` 改 `@AutoConfiguration`（该类无 @Bean 方法，零行为差异），与 guard 统一 imports 里的注解风格。
  - 评审还核实：imports 文件行序不参与 Boot 排序（由 AutoConfigurationSorter 决定）、guard 不加 ConditionalOnMissingBean 无冲突面（不注册协作 bean，双路径装载最多多一条日志）、readme init 默认值改动是文档更正（字段自首提交即 true）。复跑：guard 测试 8/8、ES 装载测试 8/8，合计 16/16 通过，全仓 test-compile 零错误。本补记中的行为变更（显式 false 不提示）与新增测试均在工作区未提交状态（guard 初版已随 166a7e7 提交）。
