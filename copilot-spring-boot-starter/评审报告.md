## 概述
`copilot-spring-boot` 的自动装配壳。最大问题是 ObjectMapperBeanPostProcessor 写好了却没接进装配（本 starter 里是死类），以及两处条件注解写法导致用户覆盖/关开关失效。

## P1
### 1. ✅ ObjectMapperBeanPostProcessor 未注册进自动装配，Jackson 增强配置全部失效
`.../autoconfig/processor/ObjectMapperBeanPostProcessor.java:33,46-57`
- 现象：该类实现 `SmartInitializingSingleton`，负责把 Spring 容器的 ObjectMapper 交给静态 `JacksonUtils`，并应用 `copilot.jackson.deserializers/serializers`、`fieldNameQuote` 等配置。但 `grep` 全仓：本 starter 内没有任何 `@Bean` 方法、AutoConfiguration.imports 条目或组件扫描引用它（web-starter 用的是另一个 `CopilotJacksonObjectMapperPostProcessor`）。【实测(子代理)：装配点 grep=0，狗蛋复核确认】
- 影响：只用 `copilot-spring-boot-starter`（非 Web）的应用里，「容器 ObjectMapper 交给 JacksonUtils」和 `copilot.jackson.*` 配置整块不生效；用户按文档写了 yml 也没有任何反应，且无报错。
- 修复：在 `CopilotAutoConfiguration` 里加 `@Bean @ConditionalOnMissingBean ObjectMapperBeanPostProcessor`；若设计意图就是让 web-starter 那个 BPP 接管，则删掉本类，避免两份实现各写一半、行为漂移。
- **修复记录（2026-09-20）**：选择注册而非删类——web 侧 `CopilotJacksonObjectMapperPostProcessor` 只做 decorate，不实现 `copilot.jackson.*`（fieldNameQuote/自定义序列化器），删本类等于 Web 应用里这些配置继续失效。`CopilotAutoConfiguration` 新增 `@Bean @ConditionalOnMissingBean objectMapperBeanPostProcessor(ObjectProvider<ObjectMapper>, CopilotJacksonProperties)`（构造器注入，去掉字段上无效的 `@Autowired`——注册为 `@Bean` 的类 Spring 仍做注入，但字段注入写法在此场景下语义含混）。时序用 `SmartInitializingSingleton.afterSingletonsInstantiated`：等所有单例（含 Jackson 自动配置的 mapper）就绪后一次性接线，避免 BeanPostProcessor 在 mapper 创建中途读半初始化对象。与 web 侧并存关系：两者共用 `ObjectMapperDecorationTracker` 守卫 decorate 只执行一次，`copilot.jackson.*` 配置应用与 `JacksonUtils` 交接不设守卫（对同一 mapper 幂等）。测试：端到端装配用例 1 例（`CopilotPropertyConditionTest.autoConfigurationStillLoadsByDefault`，验证不配属性时自动配置正常加载）。

### 2. ✅ 两个 @Bean 缺 @ConditionalOnMissingBean，用户自定义会双份装配
`.../autoconfig/CopilotCacheAutoConfiguration.java:30-38`
- `redisListenerProcessor()`、`cacheAspect()` 均无条件注册。用户自定义同类型 Bean（想改延迟、加监控）时，自动配置 Bean 照样创建 → 容器里出现两个 `CopilotCacheEvictAspect`（`@Before/@AfterReturning` 各执行两遍，双倍删除+双倍调度）和两个 `RedisListenerProcessor`（订阅消息再多叠一层重复，与主库报告 #1 叠加）。用户只能整包 `copilot.cache.enabled=false` 关掉全部功能。【代码分析，Spring 条件装配规则确定】
- 修复：两个 `@Bean` 各加 `@ConditionalOnMissingBean`；类上补 `@ConditionalOnClass(JedisUtils.class)`，防止 exclude 掉 copilot-cache 后启动直接 `NoClassDefFoundError`。
- **修复记录（2026-09-20）**：两个 `@Bean` 各加 `@ConditionalOnMissingBean`，类上加 `@ConditionalOnClass(JedisUtils.class)`（该注解在类装载前评估，`NoClassDefFoundError` 风险解除）。行为变化：用户自定义同类型 Bean 后，自动配置的对应 Bean 不再创建——此前想自定义必须先 `copilot.cache.enabled=false` 整包关掉的功能，现在可以与自动配置共存（缺失的那个由用户补）。

### 3. ✅ @ConditionalOnProperty 用 camelCase 键，kebab-case 配置关不掉开关
`.../autoconfig/CopilotAutoConfiguration.java:53,60`
- 条件用 `copilot.asyncTransaction`、`copilot.enablePostInitialize`。`@ConditionalOnProperty` 走 `Environment.getProperty` 精确匹配，不做 relaxed binding；而 Boot 官方推荐、IDE 补全默认输出的是 kebab-case（`copilot.async-transaction: false`、`copilot.enable-post-initialize: false`）。
- 影响：用户写 kebab-case 时条件读不到属性 → `matchIfMissing=true` → 明明把开关设为 false，TransactionEvents/PostInitialize 处理器仍被装配；而 `@ConfigurationProperties` 侧按 relaxed 绑定成了 false，两边判断不一致更难排查。【代码分析】
- 修复：条件 value 改成 kebab-case 规范名（字段名不变，camelCase 配置仍被 relaxed 兼容）。
- **修复记录（2026-09-20）**：原修复方向（只把注解键改 kebab-case）经回源核对后升级——读 spring-boot-autoconfigure 3.2.4 的 `OnPropertyCondition` 源码确认它走 `environment.getProperty` 字面查找、无 relaxed binding：只改注解键会把"关不掉"的方向从 camelCase 配置翻转成 kebab-case 配置（两种写法官方条件各看不见其一）。新建 `@ConditionalOnCopilotProperty` + `OnCopilotPropertyCondition`，用 `Binder.get(env).bind(name, Boolean.class)` 判定，与 `@ConfigurationProperties` 同一套 relaxed binding 规则，kebab/camelCase 两种配置形态都能关闭开关；值无法解析成布尔时抛 `IllegalStateException` 终止启动（不允许悄悄按 matchIfMissing 装配）。`CopilotAutoConfiguration` 两处条件换用新注解，属性类 `CopilotProperties` 未改动（字段仍是 camelCase 的 `asyncTransaction`）——kebab 形态由 relaxed binding 自动识别，`spring-configuration-metadata.json` 里生成的 18 项属性就是 kebab 规范名（独立评审确认）。测试 `CopilotPropertyConditionTest` 6 例：缺失默认装配 / kebab false 关 / camelCase false 关 / 显式 true 装配 / 非法值抛异常 / 端到端装配不回归。

### 4. ✅ starter 在 classpath 根携带 application.properties
`copilot-spring-boot-starter/src/main/resources/application.properties:1`
- 文件内容：`spring.main.allow-circular-references=true`。库 jar 在根携带 application.properties 是事故源：若宿主应用自己没有 application.properties，`classpath:/application.properties` 会命中 starter 这份，给整个应用悄悄打开「允许循环依赖」开关（Boot 2.6+ 默认禁止循环依赖，是刻意暴露设计问题）；若应用有自己的文件，谁生效取决于 classpath 顺序，行为不确定。【狗蛋复核确认：文件存在且仅此一行】
- 修复：删掉该文件。确需该默认值时改为文档说明，或写一个仅在属性缺失时补默认值的 `EnvironmentPostProcessor`。
- **修复记录（2026-09-20）**：文件已删除。默认值**不能只删不补**：修复过程中端到端测试实测——上游 commons-spring 的 `TransactionEvents` 在 `@PostConstruct` 里 `getBean(TransactionEvents.class)` 自引用获取静态单例，没有该开关装配直接 `BeanCurrentlyInCreationException`（测试第一版就是这个失败）。落地报告建议的第二种方案：新增 `CopilotDefaultsEnvironmentPostProcessor`（经 `META-INF/spring.factories` 注册），仅在应用未配置 `spring.main.allow-circular-references` 时以 `addLast`（最低优先级）补 `true`——用户任意源显式配置都能覆盖，不再是"jar 与应用同名文件谁被 classpath 命中"的不确定行为。⚠️ 行为变化：依赖旧 jar 内那份文件、且应用自己没写该键的升级方，现在仍得到同样默认（由 EPP 补位），无感；应用自己显式写过 `false` 的，此前可能被 jar 文件覆盖（看 classpath 顺序），现在必定生效 false——若真有应用因此启动报循环引用，属该配置的本意，需自行解循环或改配 true。readme 第 5 节同步改写。测试 `CopilotDefaultsEnvironmentPostProcessorTest`（例数与键名勘误见下）。**补记（独立评审后）**：初版 `META-INF/spring.factories` 的键写成 `org.springframework.boot.EnvironmentPostProcessor`——接口实际在 `org.springframework.boot.env` 包下，键名写错 Spring 不报错、只当没人注册，评审代理用真实 SpringApplication 对照实测（改键前加载列表 8 个 EPP 无本类、属性源里没有 copilotDefaults；改键后 9 个、值补位成功、TransactionEvents 正常装配）。初版 3 例测试直接 new 类调方法，测不出注册错误。已改对键、新增第 4 例注册断言测试（`registeredUnderCorrectFactoryKey`：SpringFactoriesLoader.loadFactoryNames 必须含本类名）；评审过程遗留的模块根 `META-INF/` 游离目录、不 clean 打包时残留进 jar 的旧 `application.properties` 均已清理，clean 构建 `jar tf` 复验两 jar 都不再带该文件。web-starter jar 根的同类 `application.properties` 同批删除（它传递依赖本 starter，EPP 随 jar 生效，默认值不丢）；readme 第 11 行"循环依赖自动解决"与第 5 节矛盾，改为"默认允许（Boot 2.6+ 默认禁止，starter 补默认值）"。

### 6. ✅ registerModule 在循环内被调 N 次 + 吞异常
`.../processor/ObjectMapperBeanPostProcessor.java:71-87,92-108`
- 同一个 `SimpleModule` 在 for 循环体内被 `registerModule` 多次，靠 SimpleModule 的 typeId=内容哈希这一 Jackson 内部细节才勉强得到「后者覆盖前者」，语义脆弱且 O(n²)；实例化失败仅 `log.error` 后 continue，用户配的自定义序列化器被悄悄丢掉，线上表现为偶发反序列化行为不符且无人知配置未生效；`Class.newInstance` JDK9+ 已废弃。【代码分析；此段当前因 #1 实际不执行，属激活后隐患】
- 修复：`registerModule` 移到循环外只调一次；`getDeclaredConstructor().newInstance()`，失败抛 `IllegalStateException` 让启动显式失败。
- **修复记录（2026-09-20）**：序列/反序列条目先收集进同一个 `SimpleModule`，循环外 `hasCustom` 判空后一次性 `registerModule`；实例化改 `getDeclaredConstructor().newInstance()` 且类型校验（非 `JsonSerializer`/`JsonDeserializer` 子类抛 `IllegalStateException`），任何失败直接终止启动；条目缺 type 或实现类时 `log.error` 后跳过该条（这是配置不完整，与反射失败区分处理）。⚠️ 行为变化：此前"配错就悄悄忽略"，现在启动报错——自定义序列化器类名写错、忘加公共无参构造的应用升级后会启动失败（配置错误当场暴露，属预期收紧）。`field-name-quote` 转义部分：核对 Jackson 2.15 后 `ObjectMapper` 无 `setCharacterEscapes`、`setFactory` 已移除，转义只存在于 `JsonFactory` 层，代码注释如实声明"同一 JsonFactory 的多个 mapper 会共同受影响"。

### 7. ✅ 装饰状态集合非线程安全
`.../processor/ObjectMapperDecorationTracker.java:14-21`
- `Collections.newSetFromMap(new IdentityHashMap<>())` 不保证线程安全。当前两个调用方都在启动线程，但 BeanPostProcessor 在并行初始化（refresh 期被 @Async 调用、ContextRefresher 并行）下可能多线程进入 `markDecorated`，竞态下同一 mapper 被判「未装饰」两次 → decorate 执行两遍（部分配置非幂等）。static 集合永不清理，devtools 频繁重启时旧 mapper 被强引用滞留。【实测(子代理)：该类无并发原语】
- 修复：用 `Collections.newSetFromMap(Collections.synchronizedMap(new IdentityHashMap<>()))`；提供 reset 或用弱引用支持上下文重启。
- **修复记录（2026-09-20）**：底层集合改 `Collections.newSetFromMap(Collections.synchronizedMap(new IdentityHashMap<>()))`（保留 IdentityHashMap 实例判等语义：内容相同但不同实例的两个 mapper 各自登记），真正的缺陷是集合本身无并发保护：`markDecorated` 本来就是一步 `add()`（本记录初稿说成"两步改一步"，经 git diff 复核勘误），裸 IdentityHashMap 的 add 内部读-改-写可被多线程交错，换 `synchronizedMap` 包装后 add 走单次加锁的 Map.put，判重+登记合一；新增 `reset()` 出口，目前仅测试调用，生产侧未接 ContextClosedEvent——devtools 重启"旧 mapper 强引用滞留"只提供了手动清理手段，未自动消除。测试 `ObjectMapperDecorationTrackerTest` 2 例：16 线程 × 200 轮对同一 mapper `markDecorated` 每轮恰一个赢家（评审实测旧实现单轮命中竞态概率约 1.5%，只跑一轮抓不到回归）/ 不同 mapper 各自独立登记。
