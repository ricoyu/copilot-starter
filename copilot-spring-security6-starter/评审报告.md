## 概述
安全自动装配壳，只有 2 个配置类。装配面有两个明确缺陷，另有一个仓库卫生问题；安全策略下限缺失（白名单无校验）是结构性风险。

## P1
### 1. CopilotSecurityFeatureAutoConfig 的 @Configuration 被注释，但仍列在 imports 里
`.../autoconfig/CopilotSecurityFeatureAutoConfig.java:32-34`
- 类头 `@Configuration` 与 `@EnableConfigurationProperties` 都被注释掉，而 `AutoConfiguration.imports` 仍注册该类。Boot 3 读到 imports 会以 lite 模式导入：`@Bean` 方法生效但失去 CGLIB 代理，类内 bean 方法互相调用会重复创建对象；properties 注入靠另一个 autoconfig（WebSecurityAutoConfig）的同名注解兜底，两个配置的装配顺序从此互相依赖——单独启用 FeatureAutoConfig 时注入直接失败。这是 9d54377 重构的遗留状态。【实测(子代理)读代码+git log】
- 修复：恢复注解（Boot3 惯例改 `@AutoConfiguration`），或从 imports 删除该行。

## P2
### 2. permitAll 白名单无安全下限校验
`.../autoconfig/CopilotWebSecurityAutoConfig.java:96-104,245-254`
- `authorize.requestMatchers(whiteList()).permitAll()` 对运维配置的列表原样透传，支持 Ant 通配但没有危险模式检查：配 `/**` 或 `/actuator/**` 就直接全放行，框架不做任何告警。csrf disable + STATELESS 对纯 Header-token API 合理，但模块同时保留表单登录路径（line 225 的 matcher 支持 x-www-form-urlencoded），存在 login-CSRF（攻击者强制受害者登录到攻击者账号）面。另外 line 212/251 两处向 `properties.whiteList` 这个可变列表 `add("/pic-code")`：重复初始化时列表持续膨胀，且两处判重条件不一致（恰好值相同）。STATELESS 下 `LoginPolicyService` 的 SINGLE/KICK_OFF 多端登录策略完全未实现。【实测(子代理)读全文件】
- 修复：白名单含 `/**`、`/actuator/**` 时启动告警；保留表单登录则对 /login 单独开 CSRF 或改纯 JSON；pic-code 注册收敛一处；文档声明 LoginPolicyService 未落地。

### 3. 旧版安全配置以 .bak 形式提交进源码目录
`.../autoconfig/CopilotWebSecurityAutoConfig.java.bak:1-249`
- 9d54377 把 249 行旧配置整文件入库。两份互相矛盾的安全配置并存：审计时易把 .bak 当现状，也存在被无脑回滚恢复旧 permitAll 的风险。【复核确认：文件存在于 src/main/java 包内】
- 修复：`git rm` 该文件，历史留在 git log。

### 4. .imports 行尾 \r 与 CRLF
`copilot-spring-security6-starter/.../AutoConfiguration.imports`
- 注册行以 CRLF 结尾。Spring 的 ImportsReader 按 readLine 解析可容忍，当前无故障；但该文件与 gateway-starter 的同名文件都带 \r，混入工具链（自定义解析、按行 diff 生成元数据）时可能踩坑，属低成本可修。【实测：狗蛋核对文件字节】
- 修复：统一 LF。

## 无问题项（本轮覆盖确认）
